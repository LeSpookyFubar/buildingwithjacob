FIELD GUIDE / 001 · SYNTHETIC TELEMETRY

Why a valid HMAC can still be replayed.

A record can pass its integrity check every time it arrives and still be a duplicate. Follow six fictional arrivals, explain three findings, and preserve what the evidence cannot tell you.

By Jacob Zepeda / BuildingWithJacob · No coding or account needed

Scope: supplied synthetic snapshots, a publicly disclosed teaching key and rule-based checks. No live spacecraft, NASA affiliation or real AI evaluation. Use a current desktop browser with JavaScript and Web Crypto.

What HMAC checksBaselineRead the arrivalsWrite the finding

Integrity is one question. Freshness is another.

HMAC combines message data, a cryptographic hash and a shared secret key to produce a message authentication code. A receiver with that key calculates the expected code and compares it with the received value. The secret is essential to the security model. RFC 2104 describes the construction.

The exercise’s signature field contains an HMAC-SHA-256 tag, rather than a public-key digital signature. The engine signs a consistent JSON representation of the record, including its timestamp, station and sequence number, and excluding the top-level tag itself.

The key is deliberately disclosed as GSZ-TRAINING-KEY-DO-NOT-USE-IN-PRODUCTION. Anyone can create a matching tag for invented or altered records. Here, a match demonstrates consistency with the supplied fields and teaching key. It does not establish a trusted sender.

Even with a properly protected secret, recalculating HMAC alone gives a receiver no memory of previous arrivals. An unchanged record carries its valid tag when delivered again. Real protocols add context and receiver state: IPsec ESP’s anti-replay processing, for example, tracks sequence numbers and a receive window alongside integrity verification. This lab illustrates the distinction; it does not implement ESP.

First, establish ordinary behavior.

In the free workstation, select 01 / Establish the baseline, then Analyze evidence. Expect 0 findings. Read the rows anyway: GS-ALPHA has sequences 100, 101, 102; GS-BRAVO has 200, 201, 202. Compare a station with itself.

The fixed reference is 2026-06-01T12:02:00Z. The newest telemetry for GS-ALPHA is 60 seconds old; GS-BRAVO’s is 50 seconds old. Neither crosses the exercise’s threshold of more than 300 seconds. Those ages stay the same tomorrow: this is a saved snapshot.

All six tags match and no configured rule fires. That establishes a baseline for these records and checks, rather than a general certificate of security.

Now keep the original arrival order.

Row 4: seen before, still intact.

Open displayed row 4, source index 3. GS-ALPHA sequence 11 repeats the value first seen at row 3, index 2. The complete records are identical, including this matching tag:

No signed field changed, so HMAC still matches. GS-BRAVO’s sequence 10 at row 2 creates no duplicate finding because it belongs to a different station.

Rows 5 and 6: a gap, then an older timestamp.

Row 5 advances GS-ALPHA from 11 to 13. Sequence 12 has not arrived at that point, so the engine records a gap. Row 6 then supplies sequence 12 with timestamp 12:00:45Z, 15 seconds earlier than the preceding GS-ALPHA arrival’s 12:01:00Z. That produces time reversal. The gap describes arrival order; sequence 12 was later observed.

Keep the rows in their original order. Sorting by timestamp would hide the pattern these rules examine. The duplicate is just 90 seconds before the fixed reference time: an observation can look recent and still have been seen before.

Turn alerts into an analyst note.

Rule names start an investigation. A benign retransmission could explain duplication. Delayed or reordered delivery could explain 13 arriving before 12; a clock change could explain a decreasing timestamp. These rows cannot establish which explanation occurred or whether anyone acted maliciously.

In Analyst notes, include the observation, an alternative and a useful next step:

In the synthetic Replay snapshot, row 4/index 3 repeats GS-ALPHA sequence 11 from row 3/index 2. Both records have timestamp 12:00:30Z and the same matching training HMAC. Row 5 skips to 13; row 6 later supplies 12 with an earlier timestamp. Retransmission and reordered delivery remain plausible. Compare acknowledgement, receiver arrival and clock logs before attributing intent. The disclosed teaching key cannot establish a trusted sender.
